# Research notes: AI Data Analyst v2

Notes from reading the code at commit `b34ad03` (Oct 2026). Everything here is checked against source unless marked as a guess or a TODO.

## One-paragraph summary

A local web app for asking questions about a CSV in plain English. You upload a CSV, it becomes a "project" stored on disk, and each project can have several chats. Each question goes to Google Gemini (`gemini-2.0-flash-exp`) with a text profile of the dataset. Gemini answers with JSON naming an output type (`exploratory`, `visualization`, `modification`) plus pandas code. The backend runs that code with `exec()` against the full DataFrame and returns printed text, a matplotlib PNG, or a downloadable CSV. Persistence is JSON and CSV files under `DATA_DIR`. No database, no auth.

## Architecture

```
React (Vite, Zustand, shadcn/ui)  --HTTP JSON-->  FastAPI (api/)
                                                   |-- routers/projects.py  -> ProjectManager, VersionManager, eda_utils
                                                   |-- routers/chats.py     -> ChatManager, ProjectManager
                                                   |-- routers/ai_query.py  -> AIAgent (one per chat, in a process dict)
                                                   |-- /static/plots, /static/downloads (StaticFiles)
                                                 src/ managers -> StateManager -> JSON files
                                                              -> VersionManager -> CSV files
                                                 AIAgent -> google.generativeai ChatSession -> Gemini
                                                         -> exec() on pandas DataFrame
```

A second, older UI, `backend/chat_analyst_ui.py` (Streamlit, "Phase 3"), imports the same `src/` managers and `AIAgent`. It is still runnable with `streamlit run chat_analyst_ui.py` from `backend/`, which is why `streamlit` is still in `requirements.txt`.

## Request flow for a question

1. `ChatInterface` calls `appStore.sendQuery(projectId, chatId, text)`.
2. `POST /api/ai/{project}/{chat}/query` with `{ "query": "..." }`.
3. Router checks project and chat exist, then `get_or_create_agent`:
   - If an agent exists in `active_agents` for this key, reuse it.
   - Else create `AIAgent`, load `current.csv`, build `generate_eda_context(df, project.name)`, call `start_chat_session`. That calls `model.start_chat()` with **no history** and sends the whole system prompt as the first user message, plus "Dataset loaded and ready for analysis."
4. `process_query` saves the user message to the chat file, sends the query to the Gemini chat session, strips a leading ```` ```json ```` / trailing ```` ``` ```` fence, `json.loads` the reply.
5. `_execute_code(code, output_type)`:
   - globals: `df`, `pd`, `plt`, `np`, `sns`. Normal builtins are available because `__builtins__` is not overridden.
   - `sys.stdout` swapped for a `StringIO` during `exec`.
   - `visualization`: expects the code to write `plot.png` in the process working directory, then moves it to `data/plots/plot_{chat_id}.png`.
   - `modification`: expects `result` to be a DataFrame, writes it to `data/temp_modifications/{chat_id}_{8 hex}.csv`, builds a summary (before/after rows and columns, new/removed columns, first 10 rows).
   - `exploratory`: the captured stdout is the result.
6. On success, saves the assistant message (explanation, code, output, paths, summary) and the serialised Gemini history to the chat JSON.
7. Router adds `plot_url` / `download_url`. The frontend ignores most of the response and reloads messages.

There is one model call per question. No tool calling, no retry loop, no self-correction when the code throws. The error text goes back to the UI.

## The prompt

`AIAgent._build_system_instruction` in `backend/src/ai_agent.py`. Main parts:

- Dataset context block (from `eda_utils`).
- Strict JSON response format with the three output types and when to pick each. "modification" is reserved for "user wants a downloadable dataset".
- Per-type rules: print for exploratory, `plt.savefig('plot.png', ...)` + `plt.close()` for charts, `result = <DataFrame>` (double brackets, never a Series) for modifications.
- Code-quality and "work on original values, don't build intermediate flag columns" guidance.
- Safe string handling: never `eval()`, use `ast.literal_eval` for stringified collections.
- Output formatting: sectioned prints, rounding, interpretation after numbers, no empty NaN tables.
- Optional `business_context` parameter. Nothing passes it.

## EDA context (`backend/src/eda_utils.py`)

Per column: dtype, non-null count, unique count. Numeric columns get `[min, max]` and nothing else. Non-numeric low-cardinality columns (≤10 unique) list every value with counts; ≤50 unique lists the top 10. Non-numeric columns where any of the first five non-null values looks like `{...}` or `[...]` are flagged with "⚠️ STORED AS STRING" and either a `ast.literal_eval` hint (parses) or a `.str.contains` hint (does not parse, e.g. `{Bike}`). Ends with the first three rows. Computed fresh each time an agent is created. `eda_context.json` path helpers exist in `utils.py`/`state_manager.py` but nothing writes it.

## Storage

```
DATA_DIR (default "data", relative to the backend cwd)
├── config.json                       AppConfig (only written by test_phase1.py; the app never calls load_config)
├── projects/<project-uuid>/
│   ├── metadata.json                 Project
│   ├── current.csv                   the active DataFrame
│   ├── versions/version_log.json     list of Version dicts
│   ├── versions/v1_<YYYYmmdd_HHMMSS>.csv
│   └── chats/<chat-uuid>.json        { chat: Chat, messages: [Message] }
├── plots/plot_<chat-uuid>.png
└── temp_modifications/<chat-uuid>_<hex8>.csv
```

JSON writes go through `safe_write_json`: write a temp file in the same directory, then `shutil.move`. CSV writes are plain `to_csv`.

## Data model (`backend/src/models.py`)

- `Project`: id, name, original_filename, created_at, updated_at, current_version, total_rows, total_columns, file_size_mb, active_chat_id, chat_ids.
- `Chat`: id, project_id, name, created_at, updated_at, message_count, gemini_chat_history (list of `{role, parts:[{text}]}`).
- `Message`: id, chat_id, role, content, timestamp, code, output_type, output, result, plot_path, explanation, thinking, modified_dataframe_path, modification_summary, judge_score, judge_feedback. `thinking` and `judge_*` are placeholders for a planned "judge agent" (Phase 5 in the plan) that was never built.
- `Version`: version_number, project_id, created_at, created_by_chat_id, created_by_message_id, file_path, file_size_mb, change_description, row_count, column_count.
- `AppConfig`: version, last_active_project_id and judge settings (enabled, threshold trigger, quality threshold), also for the unbuilt judge.

## Versioning: what exists vs what is wired

`VersionManager` has `create_initial_version`, `create_new_version` (auto-describes the diff via `detect_dataframe_changes`), `revert_to_version` (append-only: a revert creates a new version that copies the old data), `load_version_dataframe`, `cleanup_old_versions(keep_count=10)`, `get_version_stats`.

Only `create_initial_version` is called by the app. `create_new_version` and `revert_to_version` are called only from `test_phase1.py`. No router exposes versions, and the AI path never writes `current.csv`. So every project has exactly one version in practice. The "automatic version control" line on the site and the old CLAUDE.md ("every time the AI modifies the dataset, a new version is automatically created") does not match the code. Modifications are downloads only.

Set in Compose but not read: `API_HOST`, `API_PORT`. Mentioned in CLAUDE.md but unused: `DATABASE_URL`.

Run:

- Backend: `cd backend && pip install -r requirements.txt && python3 run_api.py` (uvicorn, `0.0.0.0:8000`, `reload=True`).
- Frontend: `cd frontend && npm install && npm run dev` (Vite on port 8080 per `vite.config.ts`, not 5173 as CLAUDE.md says).

- Docker: `docker compose up --build` (backend 8000, nginx frontend on 80).

## Decisions and trade-offs (as read from the code and plans)

- **Let the model pick the output type.** One JSON field routes the result to text, chart or download. Simple and easy to render, but a wrong classification either fails the request (print-only code labelled visualization returns "no plot was saved") or silently loses output (chart code labelled exploratory succeeds, leaves `plot.png` on disk and shows nothing).
- **Full DataFrame, not a sample.** Code runs against the real data in process. The model only sees the profile and three rows. Good for correctness of aggregates; means arbitrary code touches real data.
- **`exec()` instead of a sandbox.** Fast to build, no container per query. Not safe for untrusted users.
- **Files instead of a database.** Easy to inspect and back up. No concurrency control beyond atomic JSON rename.
- **Server-rendered matplotlib PNGs.** The model already knows matplotlib/seaborn well. Charts are static images, not interactive.
- **Per-chat Gemini session in memory.** Keeps conversational context so follow-ups like "now split that by city" work. Lost on restart.
- **Managers per router.** Each router builds its own `ProjectManager`/`ChatManager`/`VersionManager` instances. They are stateless wrappers over the filesystem, so this works.

Why Gemini is stated in `REBUILD_ARCHITECTURE.md` (structured JSON output, context window, Flash is fast and cheap); see Evolution, stage 4. TODO(tarang): why move from Streamlit to React, and whether the frontend was generated in Lovable first and then wired up.

## Bugs and limitations noticed

1. **Chart overwrite.** Plots are saved as `plots/plot_{chat_id}.png`, one file per chat. Every new chart in a chat overwrites the previous one, so older chart messages in that chat show the newest image (or a stale cached one).
2. **Charts likely do not load in the React UI.** `ChatMessage.tsx` uses `src={message.chartUrl}` where `chartUrl` is `/static/plots/...`, a relative path. That resolves against the frontend origin (Vite on 8080 or nginx on 80), which has no proxy to the backend. The download button does prefix `VITE_API_BASE_URL`; the image does not. `aiService.ts` has helpers that build absolute plot and download URLs from `API_BASE_URL`, but nothing calls them. Not verified by running it.
3. **Download URL when env unset.** The download button uses `` `${import.meta.env.VITE_API_BASE_URL}${downloadUrl}` `` with no fallback, so without a `frontend/.env` it opens `undefined/static/downloads/...`. `config/api.ts` has the fallback but this component does not use it.
4. **Docker CORS.** The Compose frontend is served from `http://localhost` (port 80). That origin is not in the CORS allow list in `api/main.py`, so browser calls from the Docker frontend should be blocked. Not verified by running it.
5. **History is saved but never restored.** `ChatManager.get_gemini_history` exists and the history is written after every successful turn, but `start_chat_session` always calls `model.start_chat()` with no history. After a backend restart (or `DELETE .../session`), the model has no memory of earlier turns even though the UI shows them. `REBUILD_ARCHITECTURE.md` describes the restore path; it did not survive into this code.
6. **Failed turns half-persist.** The user message is written before the model call; the assistant message only on success. A failed query leaves a dangling user message in the chat file, and the failed exchange stays in the in-memory Gemini history.
7. **No error recovery.** If generated code throws, the traceback is returned. There is no "here is the error, fix it" retry.
8. **Blocking async handlers.** The route handlers are `async def` but call the synchronous Gemini SDK and `exec()`. Each query blocks the event loop, so the server handles one query at a time. This also happens to protect the global `sys.stdout` swap and the shared `plot.png` filename from races; moving to threads or workers would expose both.
9. **`plot.png` in the cwd.** Generated code saves to the process working directory, then the agent moves it. Concurrent execution would collide.
10. **Prompt contradiction.** The system prompt says "For columns marked with ⚠️ you MUST use ast.literal_eval()", but the EDA context marks unparseable set-like columns with ⚠️ and says "DO NOT use ast.literal_eval()".
11. **Frontend 30 s timeout.** `api.ts` aborts after 30 s. A slow Gemini call plus a heavy `exec` can exceed that; the backend still finishes and saves the messages.
12. **Stale `DATA_DIR` handling** (see Config above).
13. **No upload size limit.** The whole file is read into memory.
14. **No cleanup** of `plots/` or `temp_modifications/`. `StateManager.cleanup_orphaned_plots` exists but is never called.
15. **Deprecated SDK and experimental model.** `google-generativeai` and `gemini-2.0-flash-exp` are both old; the model name may no longer resolve.
16. **System prompt as a user message.** Sent via `send_message` rather than `system_instruction`, so it lives in history and costs tokens on every turn.
17. **Stale docs in the repo.** `CLAUDE.md` mentions `pages/ProjectsPage.tsx`, `pages/AnalysisPage.tsx`, port 5173, cached `eda_context.json`, `DATABASE_URL`, `result`/`plot_path` globals in the exec scope, a "sandboxed environment", and automatic versioning. None of these match the code. The many top-level `*_GUIDE.md` files were written alongside the code and may drift similarly.

18. **Live DataFrame in `exec`.** `df` in the exec globals is the agent's own DataFrame object, so generated code that mutates it in place (`df['x'] = ...`, `inplace=True`) changes the data for every later question in that session, and skews the next modification summary's "before" counts. `current.csv` is untouched.
19. **The model never sees results.** Only the question and Gemini's JSON reply go into the session. Printed output, charts and errors are never sent back, so follow-ups rely on the code it wrote, not what that code returned.
20. **Sessions outlive their chats.** Clearing messages, deleting a chat or deleting a project does not remove the entry in `active_agents`. After clearing messages the model still remembers the old turns.
21. **Docker config gaps.** Compose sets `GEMINI_API_KEY=${GEMINI_API_KEY}`, which is empty if not exported, and python-dotenv does not override it, so the mounted `backend/.env` cannot supply the key. Compose's `VITE_API_BASE_URL` is a runtime env var on the nginx container and has no effect on the built bundle.
22. **`test_phase2.py` ignores `.env`.** It reads `GEMINI_API_KEY` with `os.getenv` and never calls `load_dotenv`.
